## 先建立一张心智地图

**Muse 把任务材料交给模型，让模型选择下一步；Hatch 推进执行，再把实际结果交回模型。记忆、持久状态和后台任务让这个过程跨越多次对话。**

本文讨论的是 Meta 的个人 Agent **Muse（muse.ai）**。Muse Spark 是模型；个人 Muse 还包含运行框架、专属计算环境、工具、状态和权限系统。公开 Model API 的示例可以帮助理解工具循环，但不能直接当成个人 Muse 的内部协议。

读这套架构时，抓住三个问题就够了：

1. **谁在推进任务？** 模型输出决策，Hatch 组织执行与下一轮输入。
2. **哪些信息能延续？** 文件、记忆和运行状态可以持久保存，本轮 Context 只选取其中一部分。
3. **动作何时真正发生？** 工具请求要经过实际执行，涉及受控操作时还要通过权限判断。

> 资料范围：研究记录截至 2026-09-23，本文整理于 2026-09-24 并复查主要官方页面。部署边界依据 Meta 的发布时架构说明；内部文件、工具与运行记录来自经授权询问 Muse 主对话后得到的回传。整理过程没有直接登录其 VM，也没有取得完整执行日志。

## 架构总览：VM 本身也是 Meta 服务端

[![Muse 架构：Meta 托管服务端包含专属 VM 和 VM 外推理服务；Hatch 在 VM 内推进任务，工具结果进入下一轮上下文](/images/guides/muse-architecture-zh.svg)](/images/guides/muse-architecture-zh.svg)

点击图可放大。图中按职责组织组件，箭头表示工作关系，不代表精确 RPC 时序或完整基础设施拓扑。

按 [Meta 安全架构说明](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)，**Hatch 位于专属 VM 的 systemd-nspawn runtime cell 内，模型推理通过代理访问 VM 外服务**。专属 VM 属于 Meta 托管服务端；VM 外还有遥测通路，平台提供持续备份。具体接入网关、用户路由、推送和 VM 调度拓扑并未在该说明中展开。

这里有两个嵌套边界：**VM 边界**和 **runtime cell 边界**。只在容器里查看进程，看到的是容器可见范围；某个服务没有出现在进程列表中，不能据此判断它位于另一台机器。

为了理解任务如何工作，可以按职责阅读这张图：

| 对象 | 学习时关注什么 |
|---|---|
| 客户端 | 用户提交目标、补充约束、查看结果和回应审批 |
| 模型 | 根据当前可见材料形成答复，或提出工具调用 |
| Hatch / harness | 准备模型输入，分派调用，收集结果，推进下一轮 |
| 工具与工作文件 | 把调用参数变成执行结果，保存产物和可再次读取的材料 |
| 状态与权限服务 | 记录任务状态，并判定受控动作能否继续 |

这个职责拆分也与 Meta 的 [Agent frameworks 文档](https://dev.meta.ai/docs/agent-frameworks)一致。表格是教学归纳，不能据此推导 Hatch 的全部内部模块。

## 跟着一次任务看 Agent Loop

假设用户说：“比较三款开发工具的部署方式，写一份报告。”下面是一个教学示例，并非某次真实执行的日志。

### 第一步：把目标变成本轮输入

运行时需要准备本轮 **Context**：用户要求、相关历史、已经获得的资料、需要遵守的约束，以及当前可用的工具定义。

模型这次能依据哪些材料作出判断，取决于这份输入。某个文件保存在工作目录里，并不意味着模型已经读过它。

### 第二步：模型提出下一步

模型可能判断还缺部署资料，于是提出一个读取网页的工具调用。也可能发现资料已经足够，直接形成答复。

工具调用首先是一份请求：要调用什么、传入什么参数。它本身不等于网页已经读到，也不等于报告已经生成。

### 第三步：执行得到可观察结果

运行时把请求交给工具或受控执行入口。工具可能返回页面内容、文件路径、运行状态，也可能返回权限拒绝、超时或其他错误。

模型随后需要根据**实际返回值**继续判断：补查一个来源、换一个办法、询问用户，或继续生成报告。

### 第四步：把结果加入下一轮

```text
目标与约束
    ↓
Hatch 准备 Context（VM 内）
    ↓
模型推理（VM 外）
    ├─ 直接形成答复 → 交付或等待用户
    └─ 提出工具调用
           ↓
       分派与执行 → 结果／错误
           └────────→ 下一轮 Context
```

Meta 的 [Tool calling 文档](https://dev.meta.ai/docs/tool-calling)展示了“模型给出调用、执行方返回结果、模型继续处理”的接口模式。这里借用的是这个逻辑关系，未假定个人 Muse 使用相同 SDK 或内部字段。

一个任务可能需要多次往返，也可能包含并行子任务。**循环表示信息反馈关系，不表示所有任务必须排成一条串行队列。**

## 记忆、历史、Context：三者各保存什么

这部分最容易被“长上下文”和“长期记忆”两个词混在一起。理解时先区分：

- **历史记录**：以前发生过哪些交互与执行。
- **持久记忆**：从经验中整理出的、以后值得使用的信息。
- **当前 Context**：这一次模型请求实际带上的材料。

Meta 的[产品设计说明](https://introducing.muse.ai/)确认，用户可以查看和编辑 Memory 文件。本次 Muse 回传的文档与工具说明，进一步呈现了几种不同的信息处理方式：

| 处理 | 输入如何变化 | 用途与信息损失 |
|---|---|---|
| 历史压缩（Compaction） | 长历史 → 摘要及保留的近期条目 | 延续当前任务；摘要会省略细节 |
| 记忆整理 | 对话与经验 → 长期事实、日志等材料 | 支持未来任务；整理产物不等于聊天原文副本 |
| Skill 按需读取 | 简介 → 具体操作说明 | 用到时加入方法和约束；读取说明不会自动授予权限 |
| 工具定义延迟加载 | namespace 概览 → 完整 schema | 让模型知道怎么调用；schema 不等于工具执行代码 |

用一个例子串起来：用户曾说“报告优先引用官方资料”。原始表达可以存在历史里，偏好可以被整理进记忆；下一次写报告时，只有相关材料进入 Context，这条偏好才成为该轮推理的依据。

**持久保存、能够检索、已经读入，是三个不同状态。** “记忆中有这件事”和“这轮模型看到了这件事”需要分别确认。

### 我们实际看到的证据

经 Muse 回传，样本中存在 7 条 `compaction_checkpoint`，包括触发类型和压缩前后 token 数。这支持“存在历史压缩检查点”的结论；记录没有提供模型字段，不能确定使用了专用压缩模型或某个固定阈值算法。

另一个容易误读的入口差异是：回传说明中的 `memory_search` 搜记忆，`chat.read_messages` 读取指定聊天；客户端另有聊天搜索。不能把某个 Agent 工具的范围，扩大为整个产品没有聊天搜索能力。

这些是 2026-09-23 的环境观察，尚未取得公开稳定接口承诺。本文也不指定记忆一定使用某个向量库、远端索引或检索算法。

## 后台任务：执行完成之后，还要判断怎么处理结果

关闭 App 后还能继续工作，依赖任务在服务端执行、进展能够被记录，以及结果有回到主任务的路径。[产品设计说明](https://introducing.muse.ai/)描述了按计划或事件开展工作，并在完成后判断结果是否值得通知用户。

为了排查一项后台任务，可以分别问四个问题：

| 阶段 | 需要回答的问题 |
|---|---|
| 触发 | 是否到了计划时间，或发生了触发事件？ |
| 执行 | 是否真的产生运行记录，状态是什么？ |
| 结果交回 | 主 Agent 是否收到可继续处理的结果？ |
| 用户收悉 | 是否决定通知，消息是否实际送达？ |

这是一种排查方法，并非声称每种后台任务都经过相同的四个物理服务。

本次回传中，有 3 条 cron 运行记录标为 `succeeded`，还有一条记忆整理 run 标为成功。另外，5 条子任务完成 handoff 可以关联到 worker 标识。它们说明存在实际运行和结果交回的样本，但**这些记录并非同一条完整链路**，不能拼接成一次已验证的“定时触发到用户收到通知”。

记忆整理 run 在某个 handoff 去重表中没有匹配行，也不能据此断言所有消息通路都没有记录。没有关联键，就保留证据缺口。

### 子 Agent 从什么背景开始

本次 Muse 回传的 `subagent.spawn` schema 表明，通用子任务会继承父 transcript 作为起点，随后分别推进工作，再由运行时交回结果。精确快照范围和裁剪规则仍不清楚，不能解释成父子此后持续共享同一份可变上下文。

这对理解协作很有帮助：**起点可以继承，后续进展需要传递。** 子任务知道委派时的背景，不代表主 Agent 自动知道它后来做过的每一步。

## 权限链路：模型提出动作后，还发生什么

官方将 PostgreSQL、凭证服务 `hatch-authd`、Sentinel、受控 connector worker 与浏览器 broker 放在 runtime cell 外。Sentinel 判定动作许可，必要时直接与客户端审批卡往返；推理与遥测代理也提供受限出口。[官方安全说明](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

把它放回前面的报告示例：生成报告和“把报告发给某人”是两个不同动作。模型即使已经形成发送请求，执行仍可能处于等待审批、被拒绝或失败的状态。后续记录必须保留这个区别。

从工程视角看，有三份信息各自承担权威：

- **模型输出**表达准备采取的动作。
- **权限状态**决定受控动作是否获准。
- **执行结果**说明动作实际发生了什么。

将这三者混成一段自然语言，容易把“打算做”“获准做”和“已经做完”混为一谈。这是本文从架构中提炼的设计启示。

## “自我改进”怎样影响下一次任务

本次回传能支持的路径是：

```text
任务经验
    ↓
整理记忆／修订技能材料
    ↓
后续 Context 读入
    ↓
后续行动改变
```

例如，把一次成功的操作步骤写入 Skill，下一次遇到相似任务时，就有了可读取的方法。这种变化首先发生在材料层。

成功的整理 run 只能说明其运行状态；是否修改了某个文件，还要查看对应产物。此次没有获得“用户 VM 内的某次自我改进任务在线修改基础模型权重”的证据。

## 哪些结论还不能画成确定的架构

| 观察或说法 | 本文采用的结论 |
|---|---|
| 容器内看不到某服务 | 容器可见性有限；不能直接判定服务在 VM 外 |
| 出现压缩记录或相关二进制字符串 | 存在机制线索；不能确认实际模型、阈值和路由 |
| 记忆搜索能找到语义相关内容 | 有检索行为；不能据此确定索引位置或算法 |
| 清理记录平均相隔约 90 分钟 | 是该记录的间隔；缺少跨多个 boot 的对应证据，不能当成 VM 重启周期 |
| 后台运行标为成功 | 该运行报告成功；不自动证明记忆已改变或用户已收到消息 |
| 平台会备份 VM | 不能由此推出任意运行都能无损恢复或任务 exactly-once |

此外，接入、推送与 VM 调度控制面的具体拓扑，完整重试／去重／恢复语义，以及记忆索引和压缩策略，仍属于本文的未知项。

## 对 Agent 开发者的启示

学习 Muse 时，值得带走的是四个可以用于审视自己系统的问题：

1. **循环可否追踪？** 能否找到这一轮模型输入、提出的调用、实际结果，以及下一轮为何继续？
2. **信息表示是否分清？** 原始记录、摘要、长期记忆和本轮输入各有用途，不能都叫“上下文”而失去边界。
3. **异步状态是否分清？** 运行成功、结果被消费、用户收到通知，应能分别观察。
4. **授权是否有独立状态？** 不能让模型自己的一句话同时充当申请、批准和完成凭证。

用这四个问题回看总图，就能把 Muse 理解成一套持续执行任务的系统：模型负责当前判断，运行时连接行动与反馈，信息管理连接不同时间点，权限系统约束实际动作。
