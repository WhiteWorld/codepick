## 先说结论

SWE-bench 的分数告诉你某个 Agent 在开源 Python 仓库上修 bug 的能力。但它不告诉你：

- 这个 Agent 在你的 TypeScript monorepo 里表现如何
- 它改代码时会不会顺手改坏你精心设计的架构
- 完成一个任务实际要花多少钱、等多长时间
- 连续跑 10 个任务，成功率是 80% 还是 30%

如果你的团队在认真考虑引入 AI 编程 Agent，**你应该在自己的仓库上跑一次评测**。这不需要复杂的基础设施——一个周末、几个典型任务、一张表格就够了。

> 核查时间：2026-08-13。本文方法论基于公开的 Agent 评测实践（SWE-bench、aider polyglot benchmark、各工具的官方文档）整理，不依赖特定工具版本。

## 一、为什么公榜分数不够用

### SWE-bench 的局限性

SWE-bench 是目前最权威的 AI 编程评测之一，但它有明确的适用范围：

| 覆盖 | 不覆盖 |
|---|---|
| Python 开源仓库 | 你的私有仓库、TypeScript/Go/Rust 项目 |
| 单文件、局部 bug 修复 | 跨文件的架构重构、新增功能 |
| 固定的测试用例 | 你团队特有的代码规范、lint 规则 |
| 一次性的 pass/fail | 代码可维护性、是否引入新 bug |

### 其他 benchmark 的问题

- **Aider polyglot benchmark**：覆盖面更广，但任务偏简单（主要是编辑单文件），且依赖 aider 的特定评测框架。
- **各工具自报的分数**：不同工具可能在评测时用了不同的 prompt 策略、不同的模型版本，横比时要小心。
- **没有 benchmark 能测你的代码规范**：你的 lint 规则、目录结构约定、命名规范——这些只有你自己的仓库能验证。

## 二、设计你自己的任务集

### 任务从哪里来

从你最近的 git 历史里找，而不是凭空编。以下是 4 类实用任务：

| 类型 | 例子 | 难度 | 为什么值得测 |
|---|---|---|---|
| **Bug 修复** | "修复登录页在 Safari 下白屏的问题" | 中 | 最接近日常需求 |
| **测试补齐** | "给 `UserService` 的 3 个公开方法补单元测试" | 低-中 | 边界清晰，容易评估 |
| **依赖升级** | "把 `react` 从 18 升级到 19，跑通全量测试" | 中-高 | 检测 Agent 处理破坏性变更的能力 |
| **重构** | "把 `utils/date.ts` 的 moment.js 换成 date-fns" | 高 | 检测 Agent 理解项目结构的能力 |

**从哪里找**：

1. 翻最近 3 个月的 git log，找已经修过的 bug。把当时的 bug 描述作为任务描述，看 Agent 能不能独立修好。
2. 找测试覆盖率低于 60% 的模块，让 Agent 补测试。
3. 找 `package.json` 里可以升级的依赖，让 Agent 处理升级。

### 任务设计原则

- **每个任务必须有明确的验收标准**：不是"改好就行"，而是"现有测试全过 + 新增测试覆盖目标行 + lint 零错误"。
- **任务描述要像真实 issue**：不要太详细（"把第 42 行的 `const` 改成 `let`"），也不要太模糊（"优化一下"）。参考你团队实际写 issue 的风格。
- **准备 5-10 个任务**：太少没有统计意义，太多评测成本太高。5-10 个不同难度的任务是比较合理的起点。
- **包含至少一个"陷阱"任务**：描述里故意写一个不合理的需求，看 Agent 会不会拒绝或提出质疑——这是 Agent 成熟度的重要指标。

## 三、定义评测指标

### 核心四维

| 指标 | 定义 | 怎么算 |
|---|---|---|
| **成功率** | 任务通过验收标准的比例 | 通过数 / 总任务数 |
| **成本** | 每个任务消耗的 API 费用 | 从 API dashboard 或工具日志提取 |
| **耗时** | 从任务提交到 Agent 给出最终结果的时间 | 墙钟时间，含等待和重试 |
| **回归风险** | Agent 修改是否引入了新 bug | 跑全量测试 + 新增测试，看是否有非预期的失败 |

### 为什么这四个指标缺一不可

- **只看成功率**：可能选了一个烧钱但准确率高的 Agent，月账单爆炸。
- **只看成本**：可能选了一个便宜但经常改错方向的 Agent，省了 API 钱但浪费了人的 review 时间。
- **只看耗时**：快的 Agent 可能粗暴跳过了理解项目的步骤。
- **不看回归**：Agent 可能修了 A 但改坏了 B 和 C，而你没有立即发现。

### 额外指标（进阶）

当你的评测流程跑顺后，可以加上：

- **首次通过率**：Agent 第一次提交就通过验收的比例 vs 需要人给反馈后修正的比例
- **人均 review 时间**：审查 Agent 的 PR 花了多少时间，和审查人类 PR 对比
- **代码质量评分**：团队 senior 对 Agent 代码的主观评分（1-5 分），关注可读性、架构一致性

## 四、评测流程

### 第一步：准备环境

```bash
# 为每个 Agent 创建独立的工作目录
git worktree add ../eval-codex-cli codex-eval
git worktree add ../eval-claude-code claude-eval

# 每个 worktree 里安装依赖
cd ../eval-codex-cli && npm ci
cd ../eval-claude-code && npm ci
```

### 第二步：统一任务描述

把所有任务写成标准格式，确保每个 Agent 拿到完全相同的输入：

```markdown
## 任务 #1：修复 Safari 白屏

**问题描述**：用户反馈登录页在 Safari 17.4 下打开后白屏，控制台报错
`TypeError: undefined is not an object`。

**验收标准**：
1. 在 Safari 17.4 下登录页正常渲染
2. 现有测试全部通过
3. 无新增 lint 错误
4. 不引入新的浏览器兼容性问题

**相关文件**：`src/pages/login.tsx`、`src/components/AuthForm.tsx`
```

### 第三步：逐个运行

**关键规则**：每个 Agent 只能拿到任务描述，不能拿到"正确答案"。评测的正确姿势是：

1. 把任务描述给 Agent
2. Agent 修改代码
3. 你运行验收标准
4. 记录结果
5. **不要在中途给 Agent 提示**——除非你在真实场景中也会给同样的提示

### 第四步：记录结果

用表格记录，例如：

| 任务 | Agent | 通过？ | 耗时 | API 费用 | 回归？ | 备注 |
|---|---|---|---|---|---|---|
| #1 Safari 白屏 | Codex CLI | ✅ | 3m42s | $0.18 | 无 | 一次通过 |
| #1 Safari 白屏 | Claude Code | ✅ | 5m10s | $0.32 | 无 | 第一次方向错了，重试后通过 |
| #2 补测试 | Codex CLI | ✅ | 2m15s | $0.09 | 无 | 覆盖了 4 个方法而非要求的 3 个 |
| #2 补测试 | Claude Code | ❌ | 4m30s | $0.45 | 1 个测试失败 | 生成的测试用了已废弃的 API |
| #3 依赖升级 | Codex CLI | ❌ | 8m00s | $0.56 | 构建失败 | 没处理 breaking changes |
| #3 依赖升级 | Claude Code | ✅ | 6m20s | $0.41 | 无 | 自动找到了 migration guide |

## 五、结果解读：什么分数才算"好"

### 不要追求绝对分数

没有通用的"及格线"。你的判断标准取决于你的场景：

- **安全优先的团队**（金融、医疗）：成功率 > 90%，回归率 = 0%，允许成本高一些
- **效率优先的团队**（初创、内部工具）：成功率 > 70%，回归率 < 10%，成本控制在预算内
- **探索阶段的个人开发者**：先看 Agent 能不能理解你的项目结构，再看其他指标

### 关注模式而非单点

5 个任务里 3 个通过了，这不叫"成功率 60%"。你应该看：

- 它在哪类任务上强？哪类弱？
- 失败的原因是什么？理解错误？能力不足？还是方向一开始就偏了？
- 修正后能不能通过？需要多少轮反馈？

### 跨 Agent 对比时的公平性

- 用同一个模型（或同级别模型）对比
- 用同一套 prompt / 系统指令
- 如果 Agent 工具支持自定义配置（如 AGENTS.md），保持配置一致
- 记录每个 Agent 的版本号，因为下周可能就更新了

## 六、把评测做成持续流程

一次性评测的价值有限——Agent 在快速迭代，你的仓库也在变化。

### 建立评测基线

- 把 5-10 个核心任务固化为评测集，存在仓库的 `eval/` 目录下
- 每次 Agent 大版本更新时重跑一次
- 每次更换 Agent 工具时重跑一次

### 轻量级持续评测

不需要每次完整跑。可以：

- 选 2-3 个代表性任务作为"快速冒烟测试"
- 每周跑一次，观察趋势
- 如果趋势变差，再跑完整评测集

---

## 总结

在自己的仓库上评测 AI 编程 Agent，核心不是追求一个好看的分数，而是**了解每个 Agent 在你的代码、你的规范、你的任务类型下的真实表现**。

一个周末的投入，换来的是几个月不用在"要不要换工具"上纠结——因为你手里有数据，而不是感觉。

记住这个流程：

1. **从 git 历史里挖 5-10 个真实任务**
2. **定义清晰的验收标准**
3. **用相同的输入跑多个 Agent**
4. **记录成功率、成本、耗时、回归**
5. **看模式，不看单点**
